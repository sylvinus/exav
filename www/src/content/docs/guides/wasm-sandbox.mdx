Two reasons to run the scanner inside a WASM sandbox:

- **You don't trust the signatures:** third-party `.ndb` sets, community YARA
  rules, anything you did not build yourself.
- **You don't trust exav.** It is a young parser of hostile input, and
  `#![forbid(unsafe_code)]` is not a boundary the kernel or a runtime enforces.
  The sandbox needs no assumption that exav's own code is correct.

The same `exav-core` engine compiles to `wasm32-wasip1` and runs under any WASI
runtime (wasmtime, wasmer, wazero) with no custom host code: you bring your own
runtime, and a bug inside exav costs a crashed sandbox rather than a compromised
host.

## Quick start

<Steps>

1. Build the WASM module:

   ```sh
   rustup target add wasm32-wasip1
   cargo build --release --target wasm32-wasip1 -p exav-core --features wasi-bin
   ```

2. Optionally strip debug names to make it smaller:

   ```sh
   cargo install wasm-tools   # if not installed
   wasm-tools strip -a target/wasm32-wasip1/release/exav-wasm.wasm -o exav.wasm
   ```

3. Scan a file under wasmtime, with the signatures mounted at `/db`:

   ```sh
   wasmtime \
     --dir /path/to/sigs::/db \
     --dir .::. \
     exav.wasm \
     /db malware.exe
   ```

</Steps>

`--dir /path/to/sigs::/db` mounts the signature directory at `/db`, and
`--dir .::.` mounts the working directory so relative paths work.

## Output

Each scanned file produces one JSON `ScanReport` on stdout; progress and errors
go to stderr:

```sh
wasmtime --dir ./sigs::/db --dir .::. exav.wasm /db *.exe 2>/dev/null | jq '.verdict'
```

```json
{"verdict":"Clean","findings":[{"label":"type","detail":"PE32+ executable"}]}
{"verdict":{"Infected":{"signature":"Win.Trojan.Agent-1234","offset":4096,"method":"Pattern"}},"findings":[]}
{"verdict":{"LimitsExceeded":{"reason":"scan-size limit"}},"findings":[]}
```

`Verdict` variants: `Clean`, `Infected`, `LimitsExceeded`, `Unscannable`,
`PasswordProtected`.

## Why this matters

Loading third-party signatures makes the signature parser part of your attack
surface: a malicious `.ndb` could aim for a parser bug, excessive allocation, or
an escape from the process. Natively, any of these reaches the host. In a WASM
sandbox:

| | Native `exav` | WASM sandbox |
|---|---|---|
| Signature trust | full host access | a memory-limited WASM instance |
| Runtime | exav itself | wasmtime or another WASI runtime |
| Blast radius | the host | the module, optionally fuel-limited |
| Custom host code | n/a | none |
| Speed | native | slower |

- **Memory is bounded:** the module cannot reach memory outside its own linear
  memory.
- **No ambient system access:** WASI limits file access to the mounted paths,
  and the module has no network.
- **Fuel limits:** wasmtime can cap instruction counts and stop a runaway module.
- **Panic isolation:** a panic becomes a wasmtime trap; the host is unaffected.

<Aside type="tip" title="No custom host code">
The module is a standard WASI command, with no custom ABI or wire protocol. The
host is the runtime itself, not code exav wrote. Any runtime supporting
`wasm32-wasip1` works.
</Aside>

## Limitations

- **No daemon mode:** each run loads the database from scratch. For
  high-throughput scanning use a native `exav --listen`.
- **No stdin:** files must be on a mounted filesystem.
- **No HTTP(S) scanning:** the module cannot make network requests.
- **Database size:** `wasm32` memory tops out at 4 GiB, and building the full
  raw ClamAV database needs more. Use a
  [prebuilt database](/guides/prebuilt-database/) for large signature sets.

## Alternatives

- **Native `exav`:** full speed and features, with host access.
- **A container:** similar isolation, but a full OS image rather than one `.wasm`
  file.
