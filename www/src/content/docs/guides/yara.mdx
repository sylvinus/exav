ClamAV loads `.yar`/`.yara` rules by default, and so does exav: rule files load
alongside ClamAV signatures and match in the same scan.

## Using YARA rules

Put rule files in your signature directory; they load recursively with
everything else:

```sh
exav -d ./sigs /data          # sigs/ contains .cvd, .ndb, and .yar files
```

A YARA detection is reported like any other:

```console
sample.bin: YARA.SomeRuleName FOUND
```

Under `--clamav-compat`, a rule from a database other than a signed `.cvd` is
named `YARA.SomeRuleName.UNOFFICIAL`, as `clamscan` names it.

YARA support is behind the default-on `yara` feature. Building with
`--no-default-features` drops it and its whole dependency tree.

## A native engine, not a wrapper

exav keeps the parser half of the [`yara-x`](https://github.com/VirusTotal/yara-x)
crate and replaces its WASM back end with a native tree-walking evaluator:

- No wasmtime, no Cranelift, no `rsa`, and no code generation at scan time.
  Depending on `yara-x` as a library pulls in a large WebAssembly runtime for its
  back end; the native engine links none of it.
- YARA-X is BSD-3-Clause, compatible with exav's MIT license, and exav reuses and
  adapts its source and test vectors under it, with attribution.

<Aside type="note">
exav's rule against deriving anything from ClamAV is about the GPL; it does not
apply to BSD-licensed YARA-X.
</Aside>

## Feature coverage

**Supported:** text, hex and regexp strings with all modifiers (`nocase`,
`ascii`, `wide`, `fullword`, `xor`, `base64`, `base64wide`, `private`); full
condition logic (boolean, `of`, counts, offsets, lengths, anchors, arithmetic,
bitwise, float, comparisons, string operators, `matches`); `for … in`,
`for … of`, `with`; integer reads (`uint`/`int` 8/16/32 and `_be`); `filesize`;
`entrypoint`; external variables (`filename`, `filepath`, `extension`,
`filetype`, `owner`); rule references; global and private rules; and the `pe`,
`math`, `hash`, `string`, `time`, `elf` and `dotnet` modules.

**Not supported**, and rejected as explicit compile errors rather than evaluated
wrongly: the `macho`, `dex`, `cuckoo`, `androguard` and other modules; `include`;
`floatN()` reads; the `wide` modifier on regexp patterns; and a few fields of the
implemented modules (`pe.rich_signature`, `pe.version_info`, resources,
`pe.signatures`, `dotnet.classes`).

<Aside type="tip" title="Rejections are visible">
exav compiles per rule, so one unsupported rule cannot drop a whole feed. Every
rejection is recorded (name and reason) and logged when the database is built.
</Aside>

## Real-world coverage

Against large public community rulesets and a commercial one, the large majority
of rules compile, and the rest are rejected as above. Matching is cross-checked
against the real `yara-x` over varied inputs, comparing the set of matching rules.

The cross-check runs yara-x as a program (`yr`) rather than linking it, which
would bring its WebAssembly runtime into exav's build. Install it with
`cargo install yara-x-cli` and run `make test-yara-diff`; without it the harness
skips, so read its output rather than only its exit code.

## Using the engine directly

The engine is `exav_core::yara`, usable as a standalone YARA library:

```rust
use exav_core::yara::{Compiler, Scanner};
let mut c = Compiler::new();
c.add_source(r#"rule demo { strings: $a = "evil" condition: $a }"#)?;
let rules = c.build();
let mut scanner = Scanner::new(&rules);
let hit = scanner.scan(b"...evil...")?.matching_rules().next().is_some();
```
