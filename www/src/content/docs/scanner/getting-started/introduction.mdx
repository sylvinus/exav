exav is a malware scanner written in Rust. It ships as one MIT-licensed binary
with a scanning CLI, a resident daemon and an ICAP server. It loads the
signature databases you already have (ClamAV's `.cvd`/`.cld`, `.ndb`/`.ldb`/
`.hdb`/`.hsb`/`.mdb`/`.msb`/`.cdb`/`.imp`/`.cbc`, and YARA `.yar`/`.yara`) and
speaks two wire protocols: `clamd`, so `clamdscan`, milters and existing tooling
talk to it unchanged, and [ICAP](/scanner/guides/icap/), so it can replace a
`c-icap` container behind a proxy or an upload service.

## Why exav

Established engines are large C codebases, and they bound their own work and then
report a file clean without saying so. ClamAV, for instance, reads a file over
about 2 GB, scans none of it, and answers `OK`. exav is a rewrite in a
memory-safe language built around one rule:

> Never report a file clean unless it was fully scanned.

A file exav could not fully examine gets a verdict of its own
(`LIMITS-EXCEEDED`, `UNSCANNABLE` or `PASSWORD-PROTECTED`) instead of `OK`. A
deployment may choose to deliver such a file anyway, but only by saying so. See
[Never a silent clean](/scanner/concepts/design-principles/#never-a-silent-clean)
for what the rule implies, and [Verdicts & exit codes](/scanner/reference/verdicts/)
for how each verdict is reported.

  <Card title="Memory-safe Rust engine" icon="rocket">
    The crates that parse hostile input are `#![forbid(unsafe_code)]`. The
    default build links no C and generates no code at run time, so the
    memory-corruption bugs behind most scanner CVEs cannot occur in exav's own
    parsers. Dependencies are another matter: see
    [Dependencies](/project/dependencies/).
  </Card>
  <Card title="Bounded memory" icon="bars">
    Most archives are walked member by member instead of being extracted whole,
    and a large member waits in a temp file under
    [budgets you set](/scanner/reference/cli/#buffering-a-stream-spill). A file over a
    bound is reported, not called clean.
  </Card>
  <Card title="Native YARA engine" icon="puzzle">
    Near-full YARA support through a native tree-walking evaluator: no code
    generation at scan time, and a pure-Rust dependency tree.
  </Card>
  <Card title="WASM sandbox" icon="seti:wasm">
    The whole engine compiles to a WASI module, so **untrusted** signatures can
    be loaded without host access, with no custom host code.
  </Card>

## What it looks like

Point it at the signatures you already have:

```console
$ exav -d ~/.cvdupdate/database suspicious.bin
suspicious.bin: Win.Trojan.Agent-1234 FOUND
```

A stream on stdin is scanned like a file:

```console
$ curl -fsS https://example.com/download.zip | exav -d ~/.cvdupdate/database -
stdin: OK
```

Load the database once and serve it over either protocol, or both (neither
protocol authenticates its clients, so bind to an interface only trusted clients
reach):

```console
$ exav --listen clamd://127.0.0.1:3310 --listen icap://127.0.0.1:1344 -d /var/lib/clamav
exav: prefork daemon: 4 workers; per-job limits: wall 120s, mem 2048 MiB, cpu 120s; recycle every 1000 jobs
exav: serving ICAP on tcp:127.0.0.1:1344 (services: avscan, srv_clamav, virus_scan; preview 4096 B)
```

One process and one loaded database replace a `c-icap` + `clamav` container
pair.

With no signatures, exav refuses to run rather than answer from near-zero
coverage:

```console
$ exav suspicious.bin
exav: no signature database loaded, refusing to run (it would report real
malware as clean). Load signatures with -d/--database or --sig-dir, or pass
--allow-no-db to use the built-in EICAR-only baseline (testing only).
```
